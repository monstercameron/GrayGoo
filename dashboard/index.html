The thesis

LLM reasoning can be crystallized into verified, reusable capabilities that cut inference on later related tasks, without cutting correctness.

A model that solves the same kind of problem tomorrow should not pay full price to think it through again. GrayGoo turns each solved task into a tested Lisp tool. Later prompts reuse or combine those tools, so the next answer costs a fraction of the first, and often nothing.

The problem

Every prompt to a language model is billed as if it were the first. Ask for a palindrome checker on Monday and again on Friday and you pay for the same reasoning twice. Prompt caches only help when the text repeats exactly, and a cached answer goes stale; a cached program does not.

The idea, in one picture

New task
  1. Model writes a Lisp tool and its tests
  2. Gates: parse, risk class (R0–R6), tests in a sandboxed SBCL REPL
  3. Pass: saved to the registry. Fail: one repair with the actual-vs-expected values

Costs full price, once.

→
Related task
  1. Cheap local search finds a saved tool that looks relevant
  2. A short question (about 100 tokens): “does this tool answer the goal?”
  3. If yes, run it in the REPL. If not, fall back to a full build

Costs a fraction.

→
Exact repeat
  1. The prompt was answered before
  2. Re-run the saved call in the REPL
  3. No model call at all

Costs nothing.

Tools also compose: once square exists, sum-of-squares is built by calling it, then mean-of-squares by calling that. The tool graph on the Agent tab shows these dependencies.

Why reuse is trustworthy, not just cheap

Tests gate every save

A tool enters the registry only after its tests pass in a fresh, sandboxed SBCL process. A wrong tool is rejected and repaired before anything can reuse it. In the live runs, this caught the model’s own mistaken test expectations too.

Every prompt has a control

Each prompt is also answered by a model with an empty registry. That is the baseline in every chart: measured tokens, measured answers, not an estimate.

Known answers

The guided demo carries answers computed by hand (144, 50, 64, 30). A reused tool that drifted would show a red cross in the Prompt log.

Narrow execution

You can type Lisp into the REPL box, but only a safe subset runs: your saved tools plus math, list and string functions, lambda, let and if. File, network, eval and funcall style access is rejected before anything executes, and the worker keeps its time and memory limits.

What we measured

Three live runs on a real model (Cerebras Qwen, real token counts, temperature 0), each with the 7 guided prompts plus 10 held-out prompts, and every prompt also answered with an empty registry:

  • 70% fewer tokens overall (about 2.7k vs 8.9k per run of 7 prompts).
  • Reused tools cost 95% less (274 vs 5.0k tokens on the reused and repeated prompts), and an exact repeat cost 0.
  • 21 of 21 guided answers correct, and 27 of 30 held-out answers correct against independent Python. With no memory the model also got 27 of 30, so reuse did not cost accuracy.
  • The no-memory run often failed to produce a working tool and still spent the tokens. The held-out misses (the same string-reversal prompt each time) were rejected by the tests, not saved.

The three runs are nearly identical because the model is near-deterministic at temperature 0: repetition shows stability, not sampling variance. Your own numbers appear live on the Agent tab; the scripted Demo model shows the same mechanism for free, with estimated token counts.

How to read the Agent tab

  1. The proof panel at the top: three headline numbers, then a line chart of tokens per prompt over time. Red = the same prompt without saved tools (dashed where predicted), blue = with them; the shaded gap is the saving. Below it: tokens, cost and waiting time saved. “Show the math” opens the arithmetic.
  2. Ask the agent: type any request (Live) or click an example (Demo). “Build, test and answer” streams what the model decided, the tests, and the REPL transcript.
  3. Prompt log: per prompt, how it was answered, tokens used vs the no-memory run, and whether the answer is correct.
  4. Tools: everything the agent has taught itself, with source, passing tests, reuse counts, and a box to call a tool directly for 0 tokens.

Simple and complex ideas to try

In Live mode try something of your own with concrete data, e.g. “write a function that run-length encodes a string, then encode aaabccdd”, followed by “now decode the result back” to watch one tool build on another.

Honest limits

  • Small samples. Tiny functions, one run per prompt. Treat the percentages as a demonstration, not a benchmark.
  • Same model on both sides. The control uses the same model at temperature 0 with an empty registry; it isolates the effect of memory, not of a better model.
  • Demo answers are hard-coded for the guided prompts. Arbitrary Live prompts have tests but no independent ground truth.
  • The sandbox is process-level, not a security boundary (see the adversarial report in the repo). The typed REPL is allow-listed, but model-written tools still run in that worker, so do not feed it untrusted prompts yet.
  • Reuse needs a good match. A vague prompt (“again”, no data) gave the model nothing to call the tool with in early live runs; prompts with explicit inputs reused cleanly.
