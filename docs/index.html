Self-Evolving Lisp Runtime

A persistent Common Lisp system that turns expensive model reasoning into tested, reusable executable capabilities — so future tasks in the same domain need progressively less inference. This page states the research thesis and the benchmarks that would confirm or refute it.

1Thesis

Research hypothesis

A persistent Lisp runtime with executable procedural memory, isolated speculative execution, transfer-based promotion, and high-speed LLM inference can improve effective application competence over time while decreasing model inference required per successful task. — plan.md §2

North-star principle

The optimization target is not how much code the model can generate. It is:

How much model reasoning can the system permanently replace with safe, reusable computation? — plan.md §93

A mature deployment should shift through three stages:

early life:    LLM reasoning dominates
middle life:   LLM synthesis + learned capabilities cooperate
mature domain: capabilities dominate, LLM handles novelty only

Learning requires transfer

  • A function that fixes one task is a patch. It becomes a learned capability only after demonstrated reuse on related tasks (plan.md §4.4).
  • A healthy system learns fewer, broader abstractions — generalized procedural families — not one function per problem. Rising capability count alone is memorization, not learning (plan.md §2).
  • Primary learning criterion (plan.md §67): held-out competence increases and model work per task decreases and capability-library growth slows. If capability count rises linearly with task count, the system is memorizing, not abstracting.
  • Model output is never trusted because the model says so. Promotion requires independent empirical evidence: tests, hidden evaluation, transfer (plan.md §85.10).

2Benchmarks

Each family ships with exposure tasks, unseen transfer tasks, adversarial transforms, and long-term replay tasks. Work starts with Family A (parsing / data transformation), 20–50 related tasks, with a no-learning baseline established first.

Task families (plan.md §81)

FamilyTask types
A — ParsingDates, CSV, nested records, logs
B — API workflowsPagination, retry, normalization, caching
C — PlanningComposition of known tools, conditional workflows
D — State transformationInventory, accounts, simple workflows
E — Fault recoveryTimeouts, bad inputs, partial failures

Required splits

  • Exposure tasks — the system may learn from these.
  • Held-out transfer tasks — unseen tasks from the same family; the primary evidence of learning vs. memorization.
  • Adversarial variants — boundary, malformed, empty, large, and reordered inputs (plan.md §21F).
  • Equivalent transformations — renamed identifiers, permuted ordering, rescaled values, injected irrelevant fields; detects evaluator gaming (plan.md §37).

Baseline ladder (plan.md §82)

BaselineConfigurationIsolates

Every self-improvement experiment also runs control groups (plan.md §38): the learned system vs. a memory-disabled baseline vs. the previous stable generation, plus an optional semantic-only variant — separating the contributions of memory, code, model changes, and runtime changes.

Key experiments (plan.md §83)

  1. Does executable memory reduce inference? — tokens, calls, and latency per task.
  2. Does dual semantic + executable memory transfer better than executable-only memory?
  3. Does skill consolidation improve retrieval and reduce negative transfer?
  4. Does rehearsal prevent state corruption under intentionally malicious candidates?
  5. Does high-speed inference improve time-to-verified-mutation, or does validation dominate?
  6. Can policy self-improvement beat the frozen base policy on held-out families?

MVP demo narrative (plan.md §80)

Domain: data transformation / synthetic API tasks. Task 1 (novel format) fails, synthesizes, and promotes a patch; Task 2 (same family) reuses the skill with fewer tokens; Task 3 (related but different) generalizes into a procedural family. Target: Task 1 takes N model calls, Task 2 takes ~1, Task 20 takes 0.

Experiment success checklist

  • Held-out success increases or remains stable
  • Average model calls / task decreases
  • Average tokens / task decreases
  • Capability reuse increases
  • Negative transfer stays below threshold
  • Capability growth becomes sublinear
  • Zero canonical-state corruption
  • Rollback works reliably

Transfer-gate defaults (plan.md §30): minimum 3 independent reuses, 0 severe negative-transfer events, held-out success at or above baseline, resource regression within budget. Thresholds are configurable and unvalidated — tuning them is itself an experiment.

3Architecture snapshot

Trust domains (plan.md §6)

Domain A — Trusted kernel
Small, externally maintained, non-self-modifiable. Owns dispatch, worker lifecycle, promotion authority, evaluation, credentials, rollback.
Domain B — Active application
Currently promoted mutable behavior: capabilities, business logic, learned abstractions, adapters, workflows. This domain may evolve.
Domain C — Speculative workers
Disposable SBCL processes. Load a known generation, run candidates against virtualized effects, may crash freely. Nothing here is canonical.
Domain D — Evaluator
Runs outside the mutable runtime. Owns hidden tests, property generators, regression sets, and promotion thresholds. No write access from the application.

Mutation pipeline (plan.md §5)

goal intake → intent normalizer → capability search
  |- capability exists -> deterministic path (no model call)
  +- capability missing -> context compiler -> Cerebras / Qwen
        -> candidate Lisp -> mutation classifier -> rehearsal orchestrator
        -> parallel workers (regression / fuzzing / differential)
        -> trusted evaluator -> transfer gate -> promotion authority
        -> versioned dispatch -> live runtime

Key invariants: no speculative candidate touches canonical state directly; no candidate alters its evaluator or the promotion authority; every promotion is attributable to evidence; every active generation is reconstructible (plan.md §85).

In: pure/local-state capabilities, Cerebras generation, isolated SBCL workers, versioned registry, contracts, unit/property tests, rehearsal, promotion, rollback, procedural-memory reuse, basic transfer measurement.

Out: schema self-migration, real external writes, payment/email effects, macro self-generation, recursive agents, policy self-modification.

Minimum convincing experiment

SBCL + Cerebras/Qwen + isolated workers + versioned capabilities
+ benchmark family + patch persistence + transfer testing + no-memory baseline

First end-to-end target (plan.md §92): novel goal → no capability → candidate → worker compile → test fail → minimal counterexample → repair → pass → temporary patch → later related task reuses it → transfer succeeds → patch becomes skill → equivalent tasks run with zero model calls.

5Learning memory

Beside executable capability memory ("what to run"), an advisory learning layer captures developer experience: how to reason. Capability learning reduces how much work the model must perform; lesson learning makes the remaining work more effective (memory.md §36). A heuristic must never become executable authority — lessons steer synthesis, capabilities do work.

Does each month of mutation history make the next mutation require fewer attempts, less context, and less inference while preserving or improving correctness? — memory.md §36, north-star for the learning layer

Lesson classes (memory.md §1)

ClassExample
FailureCursor-pagination replacements must test repeated-cursor termination
RepairCSV newline bugs live in field escaping, not row serialization
DesignPrefer composition of existing capabilities over new monoliths
Runtime-specificSBCL inlining vs. routing mutable calls through dispatch cells
Model-behaviorQwen over-refactors past green — constrain scope and green-stop

Both positive and negative lessons are stored, and facts are kept separate from heuristics: facts can be trusted once verified, heuristics need ongoing empirical evidence (memory.md §§8, 20).

Mining loop (memory.md §§4–6)

Lessons are derived, not dictated — "Qwen failed → Qwen explained → explanation becomes memory" would accumulate confident nonsense:

event ledger → cluster failures/repairs → recurring pattern
→ Qwen proposes concise lesson → replay with lesson injected (A/B)
→ compare against control → promote / reject

Retrieval and lifecycle (memory.md §§12–19)

  • Context compiler injects 0–5 lessons per synthesis call, scored by relevance × confidence × measured benefit × freshness, across layers L0 (universal) to L4 (task-specific).
  • Lifecycle: observation → candidate → replay-validated → active → generalized → principle; counterexamples refine or deprecate, and confidence decays on runtime/model upgrades until revalidated.
  • Stable lessons compile into task-family playbooks, which can themselves become executable Lisp workflows: experience → lesson → playbook → computation.

Key experiment (memory.md §34)

ConditionMemory
ANo lesson memory
BRaw previous transcripts
CRetrieved distilled lessons
DLessons + executable capability memory

Metrics: first-pass success, repair loops, tokens, LLM calls, time-to-verified-mutation, held-out success. Expectation: D > C > A, with raw transcripts possibly worse than distilled lessons. Headline metric: development acceleration = baseline time-to-verified-mutation ÷ lesson-assisted time-to-verified-mutation (memory.md §33).
